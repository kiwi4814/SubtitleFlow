# Workflow

## Stage 0 — Pick real evidence and a profile

Never require sources the title does not have.

- `single`: S.
- `source-assisted`: S + C.
- `dub`: A + D.
- `bilingual`: A + B + C.
- `full`: A + B + C + D.
- `auto`: derive every valid branch from imported roles.

S is deliberately distinct from A: S owns both the already-correct timing and the editable target text, while A is only the time-coordinate role in multi-source workflows.

## Stage 1 — Project canon

Do once per series/franchise, then version it. Store recurring canonical names, forms of address, gadgets, locations, organizations, terminology and historical/forbidden aliases. Context-sensitive aliases are never mass-replaced.

## Stage 2 — Intake

Import with `subflow source add`. SubtitleFlow copies the source into the title workspace, records SHA-256, and makes it read-only on a best-effort basis. Hash verification is authoritative.

## Stage 3 — Title research

When required, OpenCode's researcher creates `research/context.md` and `research/sources.md` before semantic editing. Stable recurring decisions belong to project canon; one-title terms remain title-scoped.

## Stage 4 — Normalize and protect authored typesetting

ASS/SSA/SRT become structured JSON. Timing, text, style, event type and raw event evidence are retained.

Editable ASS dialogue excludes:

- complex positioned/drawing/karaoke/effect events;
- non-dialogue events;
- common authored special styles selected by the active style profile (Note/注释, Title/标题, Song/歌词, Screen/Sign, Ruby, Staff, OP/ED, etc.).

This is the Hybrid safety boundary. Source special events are preserved during compile rather than regenerated by AI.

## Stage 5 — Build the active branch

### clean / single

S becomes the clean workfile directly. There is no alignment and S timestamps are preserved exactly.

### clean / source-assisted

S still owns timing. C is aligned only as source-language semantic evidence. C must never replace S timing.

### TW

A↔D uses N:M dynamic-programming alignment. A supplies video coordinates; D supplies Taiwan-dub wording.

### JP bilingual

A↔B builds Chinese work units, then C is aligned as Japanese semantic evidence. Do not match by row number.

## Stage 6 — Deterministic normalization

Apply only configured mechanical rules:

- optional OpenCC conversion;
- approved, non-context-sensitive glossary rules;
- deterministic punctuation/text normalization owned by code.

Every deterministic terminology change is recorded. Context-sensitive terms become review flags, never blind replacements.

## Stage 7 — AI semantic analysis

Default decision is KEEP.

- clean without C: language-level defects only; do not claim mistranslation verification.
- clean with C: C may support a semantic proposal.
- TW: actual dub audio/D controls wording.
- JP: C controls source semantics.

LLM output is proposal JSON, not a direct workfile edit.

## Stage 8 — Human review

Every semantic wording change requires an explicit approve/reject/custom decision. Proposal stale protection requires the candidate's `original_text` to still match the current `final_text`.

## Stage 9 — Compile with versioned style

Kiwi Collector v1 is the bundled default. It standardizes ordinary generated dialogue but uses Hybrid preservation for authored source typesetting.

Generated dialogue roles:

- `SF-ZH`: 文泉驿微米黑 60, ScaleY 105%, grey-white, Bold, 2 px outline, MarginV 103, `\blur2`.
- `SF-JA`: 文泉驿微米黑 50, warm gold, Regular, 2 px outline, MarginV 45, `\blur2`.

Styling and semantic editing are separate. Changing the style profile invalidates compile/QA/visual/release but does not require retranslation.

## Stage 10 — Deterministic QA and font audit

`subflow qa` checks source integrity, structural validity, pending review, terminology, alignment warnings, layout estimates and reparses compiled ASS.

Font audit scans every actually used Style and inline `\fn` in compiled ASS. It normalizes vertical names such as `@方正粗圆_GBK` to the same font family. Resolved font files are recorded with path, MIME type, byte size and SHA-256.

The production font gate is intentionally separate from semantic QA: unresolved fonts can be reported without making semantic/structural diagnostics disappear, but `subflow release` blocks by default until the font gate passes.

## Stage 11 — Independent semantic QA

A separate QA agent audits high-risk semantics and all human-approved changes. Corrections return to the normal human-review loop. Semantic QA must leave a non-empty report before it can be marked passed.

## Stage 12 — Render and visual approval

`subflow render` uses real video plus FFmpeg/libass. Rendering a PNG does not equal approval. Inspect actual frames for fallback fonts, clipping, collisions, safe area, line count, readability, dialogue hierarchy and preserved source typesetting.

## Stage 13 — Release freeze

`subflow release` re-verifies sources, review state, current QA snapshot, configured gates and fonts. It freezes:

- final ASS SHA-256;
- QA summary and input snapshot;
- active workflow profile and branches;
- style profile;
- font attachment file paths, names, MIME types, sizes and SHA-256 values.

Any upstream change makes the frozen release stale.

## Stage 14 — MKV Remux

`subflow remux` verifies the frozen release and font hashes before invoking MKVToolNix. Existing video/audio remain untouched. Existing MKV attachments are preserved by default. If an existing attachment has the same filename as a frozen font, SubtitleFlow uses `mkvextract` to SHA-compare it; only byte-identical content is reused, while mismatched collisions block Remux. Missing frozen fonts are added as Matroska attachments. After muxing, SubtitleFlow runs `mkvmerge -J` and confirms the required attachment names/sizes exist in the output.
