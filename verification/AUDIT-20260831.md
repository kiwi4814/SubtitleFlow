# SubtitleFlow v0.2.0 — Code Audit & Hardening Report

Date: 2026-08-31

This report audits the uploaded `SubtitleFlow-v0.2.0.zip` as the sole code baseline. It distinguishes the original package behavior from the post-audit hardening changes in this working tree. It is not a claim that every planned SubtitleFlow feature is complete.

## Executive verdict

The original v0.2.0 package was a **real, runnable Python project**, not a documentation-only prototype. Its original 42-test suite passed when independently rerun, and the S/A/B/C/D profiles were implemented in engine code. However, the baseline was **not yet safe enough for long-term archival production** because several stale-evidence and Release/Visual/Font paths could be bypassed while all original tests still remained green.

The audit hardening keeps the current architecture and fixes concrete failure modes instead of replacing the project with a new framework. The current suite contains **64 tests**, and the audited FFmpeg/libass path has been exercised with an actual synthetic video and an actual locally installed CJK font file.

Two workflow decisions are intentionally left open rather than guessed:

1. low-confidence alignment needs a durable `Approve / Adjust / Defer` review ledger;
2. after a new `prepare`, approved semantic changes should eventually be fingerprint-aware replayed or superseded, but the exact rebase policy is a product decision.

Until those are implemented, the engine now prefers **blocking stale/erased approvals** over silently releasing an inconsistent artifact.

## P0 findings fixed in this audit

### P0-01 — Unimported semantic proposals were invisible to Release

**Baseline:** a model could write a new JSON file under `review/proposals/` after QA and before Release. Until `review import` ran, the Release gate did not know it existed.

**Impact:** a semantic change request could exist in the repository while Release still reported zero pending candidates.

**Fix:** proposal JSON files are durable evidence; unimported proposals are part of QA snapshot and independently block Release. Imported files are archived under `_imported/` and their SHA/path is recorded on the candidate.

### P0-02 — Human Review stale protection only compared visible text

**Baseline:** if timing/source cue/context changed but `final_text` happened to be identical, an old proposal could still be approved.

**Impact:** semantic approval could be applied to evidence the human/model had not actually reviewed.

**Fix:** candidate fingerprints now bind unit timing/source evidence plus source manifest, canon and research context. Stale candidates are rejected.

### P0-03 — Re-prepare could erase an approved edit while the review ledger stayed approved

**Baseline:** rebuilding a workfile from source could remove the accepted text but keep the old candidate status.

**Impact:** Human Review could appear complete while the current subtitle no longer contained the approved change.

**Fix:** structural QA requires approved/custom candidates to have a matching current workfile `ChangeRecord` and accepted materialized text. Current Release therefore blocks rather than silently losing the decision.

### P0-04 — Visual render did not use the frozen/audited fonts

**Baseline:** FFmpeg used `ass=subs.ass` and relied on the host font environment. A font audit could pass on one file while preview rendering silently used a different system fallback.

**Impact:** “visual QA passed” did not necessarily validate the typography later attached to the MKV.

**Fix:** render stages the exact successful font-audit attachments into an isolated font directory and invokes libass with `fontsdir`. Render evidence freezes ASS SHA, video identity, font SHA set and preview-frame SHA set.

### P0-05 — Failed/repeated render could leave old visual evidence reusable

**Baseline:** prior frames/state were not invalidated early enough.

**Impact:** an old screenshot could continue to support a later visual approval after a failed new render.

**Fix:** render/visual/release/remux state and old frames are invalidated before rerender; successful new frames are committed only after FFmpeg succeeds.

### P0-06 — Research/Semantic/Visual gates were presence checks, not input-bound evidence

**Baseline:** a non-empty report/frame could remain “passed” after its input files changed.

**Impact:** downstream Release could claim a gate passed for a different subtitle/research/report/render.

**Fix:** all three gates now store/validate evidence snapshots. Release schema 3 freezes the gate evidence.

### P0-07 — JP bilingual compile could drop plain special Style events

**Baseline:** the JP branch preserved complex-tag events but did not pass the configured special Style-name preservation set into template rendering.

**Impact:** a Note/Title/Song/etc. event with no `\\pos`/karaoke/etc. could disappear from final ASS.

**Fix:** JP compilation now uses the same profile-driven preserved Style set as the other branches, with regression coverage.

### P0-08 — Font attachment ambiguity was not blocked

**Baseline:** two required font files with the same attachment filename but different SHA payloads could reach audit output. Explicit `font-map.json` also accepted a parseable file even when its internal family did not match the requested ASS family.

**Impact:** ambiguous/self-contradictory collector MKV font evidence and possible silent fallback.

**Fix:** same-name/different-SHA is a hard font-audit error. When FontTools is available, explicit mappings must match internal family/name metadata or configured aliases.

### P0-09 — Source replacement could hide damaged evidence and archive paths could collide

**Baseline:** replacement archive names had second-level timestamp granularity; source history did not record the archived path, and existing source integrity was not checked before replacement.

**Impact:** rapid replacements could overwrite historical evidence, and a tampered source could be moved away before being detected.

**Fix:** verify current source hash first; archive under timestamp + UUID; record archive path/SHA; reverify archive; make archived copy read-only best-effort.

### P0-10 — Remux could target the input MKV path

**Baseline:** `--force` could permit input and output path aliasing.

**Impact:** destructive replacement risk.

**Fix:** input and output resolving to the same path are always blocked.

## Other correctness fixes

- explicit `single` no longer silently becomes source-assisted merely because role C is present; only `auto` may derive that behavior;
- `style set` validates the prospective profile before writing `title.json`, avoiding configuration corruption;
- QA snapshot now includes canon JSON, proposal files and configured font-map evidence;
- selected visual-QA video identity is frozen into Release and rechecked at Remux;
- OpenCode shell permissions were narrowed so human-impacting `subflow` commands do not inherit a blanket allow.

## Remaining P0 / production blockers

### P0-OPEN-01 — Low-confidence alignment has no durable Human Review gate

Current QA reports low confidence as a warning. This does not fully satisfy the intended rule “low confidence enters Review rather than being forced through.”

**Recommended design:** add an alignment-review ledger with stable alignment IDs/fingerprints and `Approve / Adjust / Defer`. Release should require all review-required alignments to be resolved. Do not merely turn the current warning into an error; that would provide no durable unlock mechanism.

### P0-OPEN-02 — Timing QA is not yet archival-grade

The current structural checks validate basic cue ordering and overlap warnings, but there is not yet a complete production Timing QA policy for configured-video bounds, front/middle/back drift diagnostics, and extreme-duration thresholds.

**Recommended design:** keep timing ownership separate from translation. Add a deterministic `timing` QA section that probes the configured video when available and records video evidence in the QA snapshot. Policy thresholds should be configuration, not subtitle-language logic.

## P1 architecture/generalization findings

### P1-01 — Keep A/B/C/D/S externally; introduce capabilities internally later

The current role/profile system is not fake: it drives workfile/compile behavior. Replacing it immediately with a universal capability graph would add migration cost before all authority rules are modeled.

Recommended staged model:

```text
external role/profile compatibility
        ↓
internal evidence descriptor
        ↓
capabilities + authority
        ↓
stage planner
```

Likely capabilities:

- `timing`
- `editable_text`
- `source_semantics`
- `dub_wording`
- later, only if needed: `typesetting_template`, `audio_wording`

Map legacy roles to capabilities without deleting role identity. Capabilities should decide whether a stage is meaningful; roles still preserve provenance and familiar project semantics. This is the lowest-risk path from v0.2.0 to a more generic Evidence model.

### P1-02 — `prepare` needs an explicit approved-change rebase policy

Current safe behavior detects that an approved edit disappeared and blocks QA/Release. Recommended future behavior:

1. unchanged evidence fingerprint → replay the accepted edit automatically and record replay provenance;
2. changed evidence/context → mark prior candidate `superseded` and require Human Review again;
3. never silently discard or blindly replay by row/unit ID alone.

### P1-03 — Kiwi numeric style values vs source PlayRes

Kiwi Collector v1 values are authored for a 1920×1080 reference canvas, but the compiler deliberately preserves source `PlayResX/PlayResY` to avoid corrupting authored coordinate-based effects. On non-1920×1080 sources, numeric dialogue sizing/layout may therefore differ from the intended reference presentation.

Do not fix this by blindly writing `PlayResX=1920/PlayResY=1080`: protected `\\pos`, `\\move`, `\\clip`, drawings and transforms would need coordinate-safe scaling. A future profile/application policy should make this explicit and test effect geometry.

### P1-04 — Media identity is pragmatic, not cryptographic

Visual evidence currently binds video path + size + nanosecond mtime to avoid repeatedly hashing very large MKVs. This prevents ordinary accidental mismatch, but it is not adversarial-grade provenance.

Recommended: optional strict full/content hash for archival releases, with the current identity retained as a fast local mode.

### P1-05 — Font audit still cannot prove glyph coverage

Internal family matching proves that the mapped file claims the requested family; it does not prove every Chinese/Japanese glyph required by the ASS exists. Per-glyph libass fallback can still occur.

Recommended: extract code points from compiled ASS and validate cmap coverage for production fonts when FontTools is installed; visual QA remains the final display check.

### P1-06 — MKV output post-check verifies attachment identity only partially

The current post-remux `mkvmerge -J` check confirms required attachment names/sizes. Pre-existing same-name collisions are SHA-compared with `mkvextract` before mux. For even stronger archival verification, optionally re-extract required output attachments and compare SHA-256 after mux; making this mandatory would make `mkvextract` a universal Remux dependency, so it should be a deliberate policy choice.

### P1-07 — `/subtitle/run` control loop belongs in the engine eventually

The current slash command is a good UX, but “advance to next required human gate” is still agent-prompt behavior rather than a deterministic planner API. A future engine command should compute the next legal step from repository state and return a machine-readable stop reason.

### P1-08 — Rich Canon/Research authority is only partially typed

Project/title glossary data is functional and all immediate canon JSON now participates in stale QA. Rich characters/decisions/research-source authority still depends on repository conventions rather than a formal schema. Add typed schemas only when actual project usage demonstrates stable fields; avoid a speculative ontology.

## P2 usability/documentation findings

- stage name `alignment_and_seed` is misleading for S-only `single`, where no alignment occurs;
- OpenCode binary/release-channel naming can change; docs should describe the supported configuration/command structure without hard-coding a beta executable name as an invariant;
- exact Windows/macOS runtime execution has not been performed in this Linux audit environment, although path handling uses `pathlib`/argv subprocesses and tests cover portable project behavior;
- `ruff` is configured but could not be executed in this offline container; do not confuse “configured” with “lint passed.”

## Security / destructive-behavior review

Positive findings:

- subprocesses use argument lists rather than `shell=True`;
- source role/title/project IDs are constrained rather than accepted as arbitrary output paths;
- JSON state writes use atomic replacement helpers;
- source hashes are authoritative over chmod/read-only status;
- remux is stream-copy oriented rather than transcoding;
- human-impacting OpenCode shell commands are no longer blanket allowed.

Remaining operational cautions:

- read-only filesystem permissions are best-effort and are not a security boundary;
- font-map/media paths are local machine inputs and must remain user-controlled configuration;
- external tools are trusted executables from the host environment;
- model-written JSON/research content remains untrusted data and must continue to pass engine validators before state-changing actions.

## Portability review

- Python code uses `pathlib` and argv subprocess calls and has no discovered POSIX-only shell command in the runtime engine;
- declared Python range is 3.11–3.13, but this audit could execute only Python 3.13.5;
- Windows/macOS filesystem/runtime behavior remains CI/test-matrix work, not something this Linux audit can certify;
- font binaries are intentionally excluded and local font mappings are machine-specific by design;
- visual/release evidence should be regenerated when moving media/font paths between machines.
